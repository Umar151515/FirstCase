# 1. Что такое FirstCase

**FirstCase — платформа первого профессионального опыта.**

Слоган:

**«Первый заказ. Первый кейс. Реальная репутация».**

Платформа соединяет начинающих цифровых специалистов с людьми, которым нужна помощь в небольших задачах.

Целевая аудитория:

- Начинающие программисты.
- Дизайнеры.
- Видеомонтажёры.
- Художники.
- Вайбкодеры.
- Начинающие специалисты других цифровых профессий.
- Студенты.
- Небольшие предприниматели.
- Блогеры.
- Люди с небольшими задачами.

Главная проблема: начинающим специалистам трудно получить первый заказ без портфолио, но без заказов трудно сформировать портфолио.

FirstCase помогает пройти этот этап.

**Ключевая особенность — подтверждённые кейсы.**

После выполнения задачи исполнитель получает подтверждение выполненной работы и отзыв заказчика. На основе завершённого заказа он может создать кейс для портфолио.

В отличие от обычного портфолио, такой кейс связан с настоящим заказом, выполненной работой и подтверждением заказчика.

На первом этапе сервис работает в Кыргызстане, прежде всего в Бишкеке.

Интерфейс на русском языке, архитектура должна позволять впоследствии добавить кыргызский и английский.

# 3. Архитектурный эталон — Silk-Fetch

У меня есть старый проект Silk-Fetch.

Его архитектуру нужно использовать как **основной структурный образец**, но бизнес-логику Silk-Fetch переносить не нужно.

Если репозиторий старого проекта доступен — сначала изучи его:

- Структуру каталогов.
- Конфигурацию.
- Database layer.
- Dependency Injection.
- Repository pattern.
- Service layer.
- Feature modules.
- Dockerfiles.
- Docker Compose.
- Тестовые фикстуры.
- Обработку ошибок.
- Python coding style.

Особенно важно сохранить следующие идеи.

### Infrastructure Core

В `shared/core/` должны находиться:

- `config.py`
- `database.py`
- `dependencies.py`
- `exceptions.py`
- `security.py`
- `storage.py`
- `logging.py`

В `core` не должно быть бизнес-логики конкретных заказов, отзывов или пользователей.

### Vertical Feature Slices

Каждая фича должна иметь собственные:

- `models.py`
- `repositories.py`
- `services.py`
- `schemas.py`
- `exceptions.py`, если необходимо.

Роутеры FastAPI должны оставаться тонкими.

Repository отвечает исключительно за доступ к данным.

Service отвечает за бизнес-логику, транзакции, проверки и orchestration.

Все важные изменения заказов проходят через Service layer.

### Dependency Injection

Применяй DI так же последовательно, как в Silk-Fetch.

Однако учитывай важный нюанс: FastAPI `Depends` работает в контексте FastAPI, а не автоматически внутри aiogram.

Создай нормальную сборку зависимостей для бота отдельно, чтобы бот и backend могли использовать общие сервисы без дублирования логики.

Не создавай новые SQLAlchemy-сессии внутри бизнес-сервисов вручную.

Сессия должна передаваться извне.

Не делай бизнес-сервисы зависимыми от самого FastAPI.

### Database Conventions

Используй:

- `DeclarativeBase`.
- SQLAlchemy `Mapped`.
- `mapped_column`.
- `async_sessionmaker`.
- `expire_on_commit=False`.
- Naming conventions для constraints.
- Alembic migrations.
- Индексы и уникальные ограничения.
- Корректные внешние ключи.
- Явные транзакционные границы.

Не используй `Base.metadata.create_all()` как основной механизм изменения production-схемы.

# 5. Два полноценных режима запуска

Это одно из самых важных требований.

Должно существовать два независимых сценария.

## Режим A — Production / Real

`APP_MODE=production`

Это настоящий продукт.

Особенности:

- Реальная Telegram-авторизация.
- Реальные пользователи Telegram.
- Реальная PostgreSQL-база.
- Настоящие задачи.
- Настоящие отклики.
- Чат между пользователями.
- Загрузка результатов.
- Отзывы.
- Кейсы портфолио.
- Жалобы и модерация.
- Telegram-уведомления.

Никаких демонстрационных пользователей.

Никакой возможности выбрать чужую личность.

Никаких test-login endpoints.

Сервер всегда проверяет доступ по аутентифицированному пользователю.

## Режим B — Demo / Test

`APP_MODE=demo`

Это полноценная демонстрационная среда для хакатона.

Она должна работать даже без Telegram и без настоящего Telegram Bot Token.

Самое главное: **Demo должен использовать ту же бизнес-логику, что и Production.**

Нельзя создать отдельную фейковую Flutter-версию, где кнопки просто изменяют локальные картинки.

В demo должны работать настоящий FastAPI, настоящая PostgreSQL, реальные сервисы, настоящие транзакции и API.

Демонстрационные данные создаются seed-скриптом.

### Demo Identity Switcher

В демонстрационном режиме предоставь специальную панель:

**«Войти как...»**

Пользователь может переключиться на роль:

- Заказчик.
- Исполнитель.

# 6. Регистрация и авторизация через Telegram

Пользователь может быть одновременно заказчиком и исполнителем.

Не нужно создавать два разных аккаунта.

Один Telegram ID = один пользователь FirstCase.

В настоящем Telegram Mini App:

1. Flutter получает raw Telegram `initData`.
2. Отправляет его на backend.
3. Backend проверяет подпись согласно официальному алгоритму Telegram Mini Apps.
4. Проверяет `auth_date`, срок действия и целостность данных.
5. Создаёт или обновляет пользователя.
6. Выдаёт безопасную сессию или короткоживущий access token.
7. Flutter использует токен для дальнейших запросов.

**Нельзя доверять `initDataUnsafe` как подтверждению личности.**

Все идентификаторы пользователей на backend должны вычисляться из проверенной сессии, а не приниматься произвольно от Flutter.

Добавь `GET /api/v1/auth/me`.

Первый вход должен открывать простой onboarding.

Пользователь указывает:

- Специализацию.
- Навыки.
- Краткое описание.
- Город.
- При желании ссылки на работы.

Он может пропустить необязательные пункты.

Нужно поддержать Telegram avatar, username и display name.

- Статус.

- Дату публикации.

- По категории.

- По статусу.
- По городу, если указан.

## 7.4. Отклики

Он пишет:

- Почему подходит для задачи.
- Предлагаемый срок.
- Необязательный комментарий.

Заказчик получает уведомление.

Заказчик может:

- Посмотреть профиль.
- Посмотреть портфолио.
- Принять отклик.
- Отклонить отклик.

После принятия создаётся активный заказ, привязанный к выбранному исполнителю.

Нельзя выбрать двух исполнителей для одной обычной задачи.

Повторное принятие отклика должно обрабатываться корректно даже при одновременных запросах.

Исполнитель не может откликаться на собственную задачу.

# 8. Жизненный цикл заказа

Реализуй полноценную state machine.

Предлагаемые статусы:

- `published`
- `assigned`
- `in_progress`
- `submitted`
- `revision_requested`
- `accepted_pending_review`
- `completed`
- `cancelled`
- `disputed`

Можно разделить статусы объявления и самого заказа на отдельные модели.

Нужно правильно определить допустимые переходы.

### Исполнение

После выбора исполнителя он получает доступ к рабочему пространству заказа.

Внутри доступны:

- Техническое задание.
- Дедлайн.
- Согласованные правки.
- Чат.
- Прикреплённые файлы.
- Кнопка отправки результата.
- История действий.

### Сдача результата

Исполнитель нажимает:

**«Сдать работу»**

Прикладывает:

- Описание результата.
- Файлы.
- Скриншоты.
- Ссылки, если применимо.

Заказчик получает уведомление.

### Проверка

Заказчик может:

- Принять работу.
- Запросить согласованные правки.
- Открыть спор.

Контролируй количество правок.

### Успешное завершение

После принятия работы заказ переводится в:

`accepted_pending_review`

Теперь заказчик должен оставить отзыв исполнителю.

**Отзыв исполнителю обязателен для успешного закрытия заказа.**

После отправки отзыва:

`completed`

Успешное закрытие и публикация портфолио — разные операции.

Отзыв должен быть связан с конкретным завершённым заказом.

Отзыв нельзя создать на несуществующий или незавершённый заказ.

Не допускай дублирующиеся отзывы от одного участника на один заказ.

### Взаимный отзыв

Исполнитель также может оставить отзыв заказчику.

Но для исполнителя это НЕ обязательно.

Заказ должен успешно закрываться без отзыва исполнителя заказчику.

# 9. Чат между заказчиком и исполнителем

Нужен настоящий рабочий чат.

Не кнопка «Написать», которая никуда не ведёт.

Реализуй:

- Текстовые сообщения.
- Хранение истории в PostgreSQL.
- Отправку файлов.
- Скриншоты.
- Временные метки.
- Отображение автора.
- Автоматическое обновление новых сообщений.
- Скролл к новым сообщениям.
- Loading и error states.
- Проверку доступа.

В чат имеют доступ только участники заказа.

Для MVP можно использовать HTTP polling каждые несколько секунд.

Не нужно усложнять систему WebSocket, Redis Pub/Sub и брокерами, если polling обеспечивает хороший UX.

Добавь pagination для истории.

Файлы должны загружаться реально.

Нельзя позволять пользователям получать приватные вложения чужих заказов по простому угадыванию URL.

# 10. Портфолио — самая важная функция FirstCase

После успешного завершения заказа исполнитель получает возможность создать подтверждённый кейс.

Система должна различать:

1. Обычные работы, загруженные пользователем.
2. Подтверждённые кейсы из завершённых заказов.

Подтверждённый кейс имеет:

- ID исходного заказа.
- Подтверждённый статус выполнения.
- Дату завершения.
- Категорию.
- Отзыв заказчика.
- Описание выполненной работы.
- Результат.
- Необязательные доказательства.
- Настройки публичности.

Исполнитель после завершения заказа выбирает:

**«Добавить в портфолио»** или **«Не публиковать»**.

Нельзя автоматически выкладывать приватные материалы в публичное портфолио.

## Режимы портфолио

Реализуй три режима.

### Private

Кейс сохраняется в личной истории пользователя.

Он виден самому исполнителю и уполномоченной модерации при наличии оснований.

Публично не отображается.

### Anonymous

Публично отображается факт выполненного заказа без раскрытия личности заказчика.

Можно показать:

- Название или безопасное описание.
- Категорию.
- Дату.
- Подтверждение выполнения.
- Разрешённые материалы.

Личные данные заказчика, его Telegram username и приватный чат не публикуются.

### Public

Исполнитель может опубликовать полноценный кейс.

Можно включить:

- Подробности заказа.
- Работу.
- Скриншоты.
- Отзыв.
- Разрешённые доказательства.

Но публикация личности заказчика, содержимого переписки и чужих файлов требует отдельного явного согласия заказчика.

Для переписки реализуй возможность выбрать конкретные сообщения или фрагменты, а не публиковать приватный чат автоматически.

Полная публикация возможна только с явного согласия обеих сторон.

Если заказчик не согласен — исполнитель всё равно может показывать подтверждённый анонимный кейс в пределах разрешённых данных.

**Анонимность не должна зависеть от оплаты чаевых.**

# 11. Добровольные чаевые через QR

Никаких сложных платёжных интеграций.

Никакой привязки банковских карт.

Никаких транзакций внутри FirstCase.

Исполнитель может добавить в профиль:

- QR-код для чаевых.
- Изображение QR.
- Название платёжного метода.
- Необязательную безопасную платёжную ссылку.

Например, QR-код своего банковского или электронного кошелька.

После завершения заказа заказчик видит:

**«Понравилась работа? Можете поблагодарить исполнителя»**

И кнопку:

**«Оставить чаевые»**

После нажатия отображается QR исполнителя.

Заказчик самостоятельно переводит любую сумму через внешнее приложение.

FirstCase:

- Не хранит банковские реквизиты.
- Не принимает платежи.
- Не рассчитывает комиссию.
- Не подтверждает получение денег.
- Не показывает неподтверждённые переводы как реальные.
- Не требует чаевых для завершения заказа.

Можно добавить необязательную кнопку «Я отправил чаевые», но такое действие не считается подтверждением перевода.

### Чаевые и анонимность

Заказчик может предложить чаевые как благодарность и попросить не раскрывать данные заказа.

Однако право на приватность бесплатно.

Запрос анонимности не должен требовать перечисления денег.

Если у кейса нет разрешения на публикацию приватных материалов, исполнитель не может открыть их публично независимо от чаевых.

Нельзя редактировать рейтинг напрямую с клиента.

Нельзя оставлять отзывы самому себе.

Нельзя создавать отзывы без соответствующего заказа.

Добавь базовую защиту от накрутки и повторных запросов.

# 16. Flutter architecture

Не использовать старые StateNotifier-паттерны без необходимости.

Добавь централизованную обработку:

- Unauthorized.
- Forbidden.
- Validation error.
- Network error.
- Server error.
- Empty state.
- Loading state.

Все формы должны валидироваться.

Все кнопки должны иметь реальные действия.

Организуй инфраструктуру по образцу Silk-Fetch.

### Development

`docker-compose.yml`

- PostgreSQL.
- FastAPI backend.
- aiogram bot, если есть Telegram token.
- Persistent storage.
- Healthchecks.
- Hot reload Python-кода.

### Production

`docker-compose.prod.yml`

- Production build.
- Без source code bind mounts.
- Без debug endpoints.
- Без demo-auth.
- Persistent volumes.
- Нормальные restart policies.
- Healthchecks.

Frontend должен иметь понятный способ локального запуска и production build.

Настрой multi-stage Dockerfiles.

Используй `uv` и `uv.lock`.

Для production должны быть воспроизводимые версии зависимостей.

Создай `.env.example` со всеми необходимыми параметрами:

```env
APP_MODE=demo
DEBUG=true

DATABASE_URL=
TEST_DATABASE_URL=

TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_USERNAME=

JWT_SECRET=
ADMIN_TELEGRAM_IDS=

PUBLIC_WEBAPP_URL=
API_PUBLIC_URL=

UPLOAD_DIR=
MAX_UPLOAD_SIZE_MB=10

CORS_ORIGINS=
```

Это примеры, расширяй при необходимости.

Demo должен запускаться без Telegram credentials.

Production не должен запускаться без необходимых секретов.

Нельзя запускать production с демонстрационным JWT secret.

# 26. Требования к качеству исполнения

На каждом этапе:

1. Создавай реальные файлы.
2. Проверяй импорты.
3. Выполняй анализ Dart-кода.
4. Проверяй Python lint.
5. Запускай тесты.
6. Проверяй API-контракты.
7. Исправляй найденные ошибки.
8. Продолжай следующую фазу.

Никаких несуществующих импортов и выдуманных методов библиотек.

Никаких обращений Flutter к несуществующим API endpoints.

Никаких DTO, несовместимых с backend schemas.

Никаких кнопок, которые визуально существуют, но не выполняют действий.

Никаких зашитых demo-данных в production-логике.

Если среда не позволяет выполнить конкретный тест или собрать Flutter Web, явно сообщи об ограничении. Не утверждай, что проверки прошли, если они не запускались.

# 29. Требования к твоей работе как AI-разработчика

Ты должен действовать автономно.

Не спрашивай разрешения на каждый следующий файл или компонент.

Не останавливайся после генерации архитектурного плана.

Не заканчивай ответ фразой «Теперь можно приступить к реализации».

**Приступай к реализации самостоятельно.**

Если контекст проекта доступен — сначала изучи его.

Если доступны терминал, файловая система и необходимые инструменты — используй их.

Работай итеративно:

**Implement → Run → Test → Fix → Continue.**

После каждого крупного этапа кратко фиксируй:

- Что реализовано.
- Какие файлы добавлены.
- Что проверено.
- Какие ошибки исправлены.
- Что осталось.

Не создавай ложных отчётов о прохождении тестов.

Если реализация не помещается в одну итерацию, оставь рабочее состояние репозитория, документируй следующий конкретный шаг и продолжай, пока это позволяют доступные инструменты.

## ВАЖНЕЙШИЙ ПРИНЦИП

Мне не нужен красивый проект, состоящий из моков.

Мне не нужен backend, у которого нет реального frontend.

Мне не нужен frontend, не подключённый к backend.

Мне не нужна архитектура ради архитектуры.

**Мне нужен красивый, удобный, действительно работающий FirstCase, который можно открыть на хакатоне, продемонстрировать жюри и после этого продолжить развивать как настоящий продукт.**

## Начинай сейчас

Сначала изучи текущие файлы и архитектурный образец Silk-Fetch.

Проверь совместимость технологического стека.

Затем создай основу FirstCase и последовательно реализуй все обязательные функциональные сценарии.

Главный результат — рабочий проект в репозитории, а не текстовое описание проекта.
